# 付费股票报告部署与运行

本文面向系统维护者，说明配置、启动、服务器部署和日常操作。架构原理见[系统架构文档](付费报告系统架构.md)。更新日期：2026-09-18。

命令中的 `ORDER_ID`、`DELIVERY_ID`、`reports.example.com` 都是占位内容，需要换成自己的订单号、邮件记录号或域名。密钥只写在本地配置文件或服务器环境中，不要提交到 Git。

常用入口：[本地预览](#2-在当前电脑预览) · [配置参数](#3-配置项说明) · [FMP 数据源](#34-fmp-数据源配置与回滚) · [Docker 部署](#5-使用-docker-compose-部署) · [域名与 HTTPS](#6-域名和-https-入口) · [订单查询与导出](#7-按订单离线查询和导出) · [备份恢复](#8-备份与恢复) · [常见问题](#10-常见问题)。

## 1. 先选择运行方式

| 目的 | 方式 | 是否需要域名及外部服务 |
| --- | --- | --- |
| 本地运行首页和购买接口 | 当前电脑直接运行 Python 服务 | 需填齐当前 Creem 模式及共用配置；完整付款回调需公开地址 |
| 查询旧订单、导出报告和备份 | 离线命令行 | 不需要域名、Creem、Resend 或模型密钥 |
| 完整验证付款、分析和收件 | 可公开访问的 HTTPS 测试站点 | 需要 Creem 测试配置、模型配置及有效发信域名 |
| 向用户正式售卖 | 单台 Linux 服务器，Docker Compose 加 HTTPS 反向代理 | 需要正式域名、Creem 正式配置及 Resend 配置 |

当前是单进程、单分析线程方案。不要增加 Uvicorn worker 数量，也不要运行多个网站副本共同处理一个数据目录。原生 Windows 不能直接使用本实现的 `fcntl` 文件锁，应通过 Linux 环境运行。

## 2. 在当前电脑预览

### 2.1 已有当前项目环境

本仓库当前已有 `.venv` 环境和付费网站入口。先按第 3 节补齐 `.env`，再在终端执行：

```sh
cd /Users/chengshuo/PycharmProjects/TradingAgents
COMMERCE_PUBLIC_URL=http://localhost:8000 \
.venv/bin/tradingagents-mvp serve --mode test
```

打开 [http://localhost:8000](http://localhost:8000)。缺少当前模式的支付、邮件或启用的人机验证配置时，命令会列出缺少的变量并直接退出，不会启动一个购买按钮不可用的网站。配置完整且任务容量正常时可以购买。按 `Ctrl+C` 停止服务。

上述临时环境变量只用于这一条启动命令，不会改写 `.env`。默认数据目录是当前系统用户家目录下的 `~/.tradingagents/commerce`，不是项目里的 `reports` 目录。

如果 8000 端口已被占用，可以同时修改访问地址与监听端口：

```sh
COMMERCE_PUBLIC_URL=http://localhost:8017 \
.venv/bin/tradingagents-mvp serve --mode test --port 8017
```

此时打开 [http://localhost:8017](http://localhost:8017)。`COMMERCE_PUBLIC_URL` 用于构造对外链接和检查网页来源，`--port` 才决定实际监听端口，两者作用不同。

### 2.2 新机器安装

进入项目根目录后执行。项目声明支持 Python 3.10 及以上，这里使用与 Docker 一致的 Python 3.12；已有 `.venv` 时无需重新创建。

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e '.[mvp]'
source .venv/bin/activate
```

如果已有环境由 `uv` 创建且没有 `pip`，可使用已有的 `uv`：

```sh
uv pip install --python .venv/bin/python -e '.[mvp]'
source .venv/bin/activate
```

`.[mvp]` 会安装 FastAPI、页面模板和报告安全渲染等可选依赖。环境激活后，本文后续的 `tradingagents-mvp`、`python` 命令都使用该环境。

若找不到控制台命令，可以使用等价入口：

```sh
python -m tradingagents.mvp.cli serve --mode test
```

### 2.3 首次配置文件

只有项目根目录还没有 `.env` 时，才从模板复制。已有 `.env` 时直接编辑它，保留原先能正常运行 TradingAgents 的模型配置。

```sh
cp -n .env.example .env
```

程序启动时读取 `.env`，但不会覆盖操作系统中已设置的同名环境变量。`serve --mode` 优先于环境变量和 `.env` 中的 `CREEM_MODE`；两者均未设置时使用 `test`。启动参数不改写 `.env`。修改配置后需要重启进程。

## 3. 配置项说明

### 3.1 在同一个文件中保存两组 Creem 配置

下面内容写入同一个 `.env`。只有 Creem 凭据分测试和正式两组，域名、邮件、人机验证、模型和限流配置共用。空值是待填写占位；启动时只要求所选 Creem 模式的那一组配置完整，另一组可以留空：

```dotenv
COMMERCE_PUBLIC_URL=http://localhost:8000
CREEM_MODE=test
CREEM_TEST_PRODUCT_ID=
CREEM_TEST_API_KEY=
CREEM_TEST_WEBHOOK_SECRET=
CREEM_PROD_PRODUCT_ID=
CREEM_PROD_API_KEY=
CREEM_PROD_WEBHOOK_SECRET=
RESEND_API_KEY=
COMMERCE_EMAIL_FROM=
COMMERCE_SUPPORT_EMAIL=
COMMERCE_RECAPTCHA_ENABLED=true
RECAPTCHA_SITE_KEY=
RECAPTCHA_SECRET_KEY=
```

```sh
tradingagents-mvp serve --mode test  # 读取 CREEM_TEST_*，使用 Creem 测试 API
tradingagents-mvp serve --mode prod  # 读取 CREEM_PROD_*，使用 Creem 正式 API
tradingagents-mvp serve              # 读取 CREEM_MODE，缺省为 test
```

升级已有配置时，将原 `CREEM_PRODUCT_ID`、`CREEM_API_KEY`、`CREEM_WEBHOOK_SECRET` 移到对应的 `CREEM_TEST_*` 或 `CREEM_PROD_*`。程序不再读取未区分环境的旧字段，也不会借用另一环境的密钥。

### 3.2 网站、支付和邮件配置

| 配置项 | 含义 | 默认值或填写要求 |
| --- | --- | --- |
| `COMMERCE_PUBLIC_URL` | 用户访问网站的完整域名地址 | 默认 `http://localhost:8000`；正式填写如 `https://reports.example.com`，不带路径、查询参数或末尾斜杠 |
| `COMMERCE_DATA_DIR` | 订单数据库及报告存储目录 | 本地默认 `~/.tradingagents/commerce`；必须使用持久磁盘 |
| `CREEM_MODE` | 默认 Creem 环境 | 默认 `test`；`serve --mode test/prod` 优先；`prod` 要求 HTTPS 网站地址 |
| `CREEM_TEST_PRODUCT_ID` / `CREEM_PROD_PRODUCT_ID` | 两个环境各自的售卖产品 | 有效的一次性付款产品；价格、币种、税费方式由 Creem 决定 |
| `CREEM_TEST_API_KEY` / `CREEM_PROD_API_KEY` | 两个环境各自的商户 API 密钥 | 与所选模式的产品对应 |
| `CREEM_TEST_WEBHOOK_SECRET` / `CREEM_PROD_WEBHOOK_SECRET` | 两个环境各自的支付通知验签密钥 | 对应本网站 Webhook，不能用 API 密钥代替 |
| `RESEND_API_KEY` | 邮件服务密钥 | 用于向付款邮箱发信 |
| `COMMERCE_EMAIL_FROM` | 发件人地址 | 如 `reports@mail.example.com`，发信域名应完成验证 |
| `COMMERCE_SUPPORT_EMAIL` | 客服联系地址 | 填写自己能收到并处理邮件的地址 |
| `COMMERCE_RECAPTCHA_ENABLED` | 创建订单前验证 Google reCAPTCHA v2 | 默认 `true`；只有 `CREEM_MODE=test` 允许设为 `false`，正式环境必须开启 |
| `RECAPTCHA_SITE_KEY` | v2 “我不是机器人”复选框的网站密钥 | 公开在购买页；开启验证后必填，不是 Gemini 的 `GOOGLE_API_KEY` |
| `RECAPTCHA_SECRET_KEY` | reCAPTCHA 服务端验证密钥 | 仅保存在服务端；开启验证后必填，不能写进前端或提交 Git |
| `COMMERCE_CHECKOUT_RATE_LIMIT` | 每 IP 创建订单的请求限额 | 默认 5 次/滚动 60 秒，必须是正整数；失败请求也计数 |
| `COMMERCE_READ_RATE_LIMIT` | 每 IP 状态查询和报告访问的共享限额 | 默认 60 次/滚动 60 秒，必须是正整数 |
| `COMMERCE_FORWARDED_ALLOW_IPS` | 信任哪些代理传来的访客 IP | 默认 `127.0.0.1`；按实际代理链路配置，不要填写 `*` |
| `COMMERCE_MAX_PENDING_RUNS` | 暂停新购买的活动任务数量阈值 | 默认 3，最小 1；包含排队、执行中及请求停止的任务 |
| `COMMERCE_STALLED_AFTER_SECONDS` | 任务运行过久时暂停新购买的阈值 | 默认 1800 秒，最小 60；不是强制终止时间 |

价格只在 Creem 商品中配置，没有本地价格环境变量。首页展示后端读取的价格、币种和税费方式，成功结果缓存 60 秒；新下单时重新读取。若页面打开后价格变化，接口返回 409，提示刷新页面确认新价格。商品不可用或读取失败时停止下单，不使用旧价格继续收费。

订单保存下单时的金额、币种和税费方式，支付通知按订单快照核验，后续调价不会重写旧订单。`inclusive` 表示页面价格已含税，`exclusive` 表示税费由 Creem 在收银台计算后加收。升级时自动为历史订单补充 `inclusive`，保留原金额和支付记录。

没有销售开关。必填项缺失会在监听端口、创建数据库和启动后台任务之前报错；直接使用应用工厂启动也执行相同校验。校验完整性不等于远端凭据已被服务商验证，真实产品、支付和交付仍按正常流程校验。离线查询、导出和备份不要求这些配置。

### 3.3 模型配置

沿用原来 Trade 分析能正常运行的模型供应商、两个模型 ID、服务地址和密钥，不要把付款参数当作模型参数。

| 配置项 | 含义 |
| --- | --- |
| `TRADINGAGENTS_LLM_PROVIDER` | 模型供应商；自定义兼容接口使用 `openai_compatible` |
| `TRADINGAGENTS_QUICK_THINK_LLM` | 快速分析使用的模型 ID |
| `TRADINGAGENTS_DEEP_THINK_LLM` | 深度研究/判断使用的模型 ID |
| `TRADINGAGENTS_LLM_BACKEND_URL` | 自定义模型服务地址，使用该服务实际要求的接口根地址 |
| `OPENAI_COMPATIBLE_API_KEY` | 使用自定义 OpenAI 兼容服务时的密钥；其他供应商使用项目对应密钥变量 |
| `TRADINGAGENTS_LLM_MAX_RETRIES` | 付费分析未设置时默认重试 2 次；可设为 0 |
| `TRADINGAGENTS_MAX_TOKENS` | 付费分析未设置时每次输出最多 8192 tokens |

例如已有兼容服务时，按下面格式替换占位内容；这不是可直接调用的真实服务配置：

```dotenv
TRADINGAGENTS_LLM_PROVIDER=openai_compatible
TRADINGAGENTS_LLM_BACKEND_URL=https://your-model-provider.example/v1
TRADINGAGENTS_QUICK_THINK_LLM=your-verified-quick-model-id
TRADINGAGENTS_DEEP_THINK_LLM=your-verified-deep-model-id
OPENAI_COMPATIBLE_API_KEY=replace-with-your-key
TRADINGAGENTS_LLM_MAX_RETRIES=2
TRADINGAGENTS_MAX_TOKENS=8192
```

模型地址不能携带用户名、密码、查询参数或片段，密钥要通过对应环境变量提供。付费报告语言优先采用用户选择，不受 `TRADINGAGENTS_OUTPUT_LANGUAGE` 的默认值控制；讨论深度固定为 1，付费任务禁用断点续跑。

模型配置在创建订单时保存快照，修改配置主要影响后续创建的订单。健康检查不会真的调用模型验证密钥或额度，开放销售前仍需验证实际分析能完成。

### 3.4 FMP 数据源配置与回滚

默认值按入口区分：付费网站（`tradingagents-mvp serve` 的 test/prod 模式，以及直接调用 `create_app()`）默认使用 FMP 行情、证券资料、基本面、三张财报、新闻和内部人交易，指标由 `local` 计算；本地 CLI/Web 默认仍使用 `yfinance`。在 `.env` 填写密钥，并保持下面五个供应商选择器未设置，即可保留两套默认值：

```dotenv
FMP_API_KEY=replace-with-your-key
```

| 配置项 | 对应分类及作用 | 付费网站默认 | 本地 CLI/Web 默认 |
| --- | --- | --- | --- |
| `FMP_API_KEY` | FMP stable API 密钥，仅从环境读取，不保存到订单 | 空；使用 FMP 时必需 | 使用 Yahoo 无需填写 |
| `TRADINGAGENTS_CORE_STOCK_VENDOR` | `core_stock_apis`：日线、行情校验、收益复盘及本地指标行情输入 | `fmp` | `yfinance` |
| `TRADINGAGENTS_TECHNICAL_INDICATORS_VENDOR` | `technical_indicators`：本地 stockstats 计算 | `local` | `yfinance` |
| `TRADINGAGENTS_INSTRUMENT_VENDOR` | `instrument_data`：公司身份和股票购买资格 | `fmp` | `yfinance` |
| `TRADINGAGENTS_FUNDAMENTAL_VENDOR` | `fundamental_data`：概览和三张财报 | `fmp` | `yfinance` |
| `TRADINGAGENTS_NEWS_VENDOR` | `news_data`：个股/全球新闻及内部人交易 | `fmp` | `yfinance` |

这些环境变量覆盖所有共用该环境的入口。原 `.env` 中如果还有 `marketstack/local/marketstack` 或 Yahoo 的显式覆盖，升级代码不会覆盖这些选择；删除或注释后才恢复入口默认值。显式传入 `CommerceService(base_config=...)` 时完整尊重调用方配置，不再应用商业默认值。付费服务使用独立配置副本，不修改本地工作台或全局默认。

修改后重启进程；Docker 按[配置生效步骤](#54-停止更新与配置生效)重建容器。`serve --mode test|prod` 只切换 Creem，不切换数据供应商。健康检查不调用 FMP 校验密钥、套餐或额度；缺少密钥会在购买资格校验时失败。公司资料接口成功也不能证明其他接口权限完整，开放销售前需执行第 11.3 节验收。

代码中对应 `config["data_vendors"]`；`tool_vendors` 优先级更高。行情工具覆盖 `get_stock_data` 同时影响指标输入、校验和复盘，`get_instrument_info` 控制身份及购买资格。`technical_indicators=yfinance` 会明确请求 Yahoo 行情，切换价格源时需一起选 `local`。仅按显式逗号分隔供应商链回退，单独配置 `fmp` 不会自动请求 Yahoo；`default` 可尝试所有注册供应商，不适合限定数据来源的部署。

FMP 适配范围为美国上市股票/ETF；OHLC 取分红复权行情，原始成交量取未复权接口，按证券和交易日合并。接口之间缺失日期或复权字段时报告不可用，不混入未复权价格。输出实际供应商和最新交易日，日线不描述成实时行情。`BRK.B`/`BRK-B` 精确映射同一类别，不按名称猜证券。SPY 可作行情/基准但不能购买报告；证券类型未知、上市交易所不支持或上游不可用均阻止创建订单。美国上市 ADR 按上市交易所判断，不按公司总部国家排除。

基本面概览组合当前 profile、quote、TTM 比率和关键指标，缺失字段标为 `N/A`，历史日期不返回今天的概览。财报保留期间、币种、披露日期；无可验证披露日期或披露晚于截止日的记录被排除，但这不提供历史重述版本。新闻分页、过滤日期并去重；`global_news_queries` 仅作用于 Yahoo 搜索。内部人交易为最新最多 100 条，显示交易日和披露日，不宣称是历史时点查询。

订单保存下单时的 `data_vendors` 和 `tool_vendors`；付款入队及运行沿用快照，不保存密钥。修改配置只影响新订单，原订单仍需原供应商凭据。行情及证券资料缓存按供应商隔离，无需清理 Yahoo/Marketstack 缓存即可启用 FMP。

**切换与回滚：** Marketstack 仍可提供行情和证券资料：填写 `MARKETSTACK_API_KEY`，将 `TRADINGAGENTS_CORE_STOCK_VENDOR`、`TRADINGAGENTS_INSTRUMENT_VENDOR` 设为 `marketstack`，指标设为 `local`；基本面和新闻继续独立选择，付费默认仍为 FMP。完全回到 Yahoo 时，五个选择器均设为 `yfinance` 并移除冲突工具覆盖。删除选择器恢复付费 FMP、本地 Yahoo，不能以删除覆盖的方式将付费入口回滚到 Yahoo。回滚不改写旧订单。

**商业授权：** `fmpsdk` 的 BSD 许可证只覆盖代码。FMP 数据展示或再分发需要相应商业协议，不能将个人付费套餐或可访问接口视为付费报告授权。按实际合同确认新闻、财报、图表、衍生结果和缓存用途；宏观、预测市场及社交来源也有各自授权。参见 [FMP 商业方案](https://site.financialmodelingprep.com/developer/docs/pricing?planType=commercial)。

## 4. 配置 Creem、Resend 和人机验证

### 4.1 Creem 测试环境

1. 在 Creem 测试环境创建一个产品，付款类型为 `onetime`，设置售价、币种和税费方式（`inclusive` 含税，或 `exclusive` 结账时另计税费）。保持产品可用，当前不支持折扣或由买家自定金额。
2. 把产品 ID 和同一环境的 API 密钥写入 `CREEM_TEST_PRODUCT_ID`、`CREEM_TEST_API_KEY`。
3. 注册 Webhook 地址 `https://你的域名/api/webhooks/creem`，订阅 `checkout.completed` 和 `refund.created`。
4. 把该 Webhook 的签名密钥写入 `CREEM_TEST_WEBHOOK_SECRET`。
5. 使用 `tradingagents-mvp serve --mode test` 启动，先做测试支付。

Creem 无法访问你电脑上的 `localhost`。本地页面可使用本地地址；完整测试付款通知时，需要把公开 HTTPS 地址填入共用的 `COMMERCE_PUBLIC_URL` 并配置外部通知。事件与验签机制见 [Creem 官方说明](https://docs.creem.io/code/webhooks)。

本地订单通过 `request_id` 与收银台关联，用户的付款成功跳转页不能代替 Webhook。测试付款后即使关闭浏览器，只要后端收到有效通知，分析仍应继续。

### 4.2 Resend 发信

1. 在 Resend 添加自己持有的发信域名或子域名，例如 `mail.example.com`。
2. 按控制台提供的 DNS 记录完成验证；记录名和值以自己的控制台为准。
3. 创建发送密钥，填写 `RESEND_API_KEY`。
4. 填写 `COMMERCE_EMAIL_FROM` 和 `COMMERCE_SUPPORT_EMAIL`；报告链接属于私密访问凭证，关闭该类邮件的点击跟踪。
5. 测试实际收件，并检查 Resend 的发送、投递和退信记录。

验证域名和子域名的要求见 [Resend 官方说明](https://resend.com/docs/dashboard/domains/introduction)。仅在 `.env` 中写上发件人地址不会自动完成 DNS 验证，也不会自动创建客服邮箱。

### 4.3 切换正式环境

在同一个 `.env` 中填写 `CREEM_PROD_PRODUCT_ID`、`CREEM_PROD_API_KEY`、`CREEM_PROD_WEBHOOK_SECRET`，确认共用的 HTTPS 域名和 reCAPTCHA 配置有效，然后运行 `tradingagents-mvp serve --mode prod`。也可把 `CREEM_MODE` 改为 `prod` 后直接 `serve`；不需要第二个 env 文件。

`--mode` 只选择 Creem 的产品、密钥和 API 地址，不自动切换数据目录、邮件、模型或其他配置。若需要保留独立测试数据，可用现有全局参数 `tradingagents-mvp --data-dir /path/to/test-data serve --mode test` 显式指定目录。

完成实际付款/报告/收件验收后再开放正式销售。模型和金融数据源的商用资格、数据范围和成本需要自行核实，程序不会替你完成这些检查。

### 4.4 Google reCAPTCHA v2

1. 在 [reCAPTCHA 管理控制台](https://www.google.com/recaptcha/admin/create) 注册 **v2 “我不是机器人”复选框**密钥。本实现使用 `api.js` 和 `siteverify`，不是 v3 分数模式或 Enterprise assessments 接口。
2. 将实际购买站点域名加入允许列表，并保留 Google 的域名校验。后端还会核对验证响应的 `hostname` 与 `COMMERCE_PUBLIC_URL` 中的主机名完全一致。
3. 填写 `RECAPTCHA_SITE_KEY`、`RECAPTCHA_SECRET_KEY`，保持 `COMMERCE_RECAPTCHA_ENABLED=true`，重启服务。缺少任意密钥会直接拒绝启动并提示变量名。
4. 本地真实联调使用独立的开发密钥，并允许 `localhost`。只有不连接 Google 的本地模拟测试才临时设 `COMMERCE_RECAPTCHA_ENABLED=false`，且必须保持 `CREEM_MODE=test`。正式模式会拒绝关闭验证或使用 Google 公共测试密钥；公共测试密钥返回的测试主机名也无法通过本应用的真实域名核对。

验证在股票查询、创建本地订单和调用 Creem 之前完成。Google 验证失败或域名不匹配返回 403，超时、异常响应或密钥错误返回 503；均不会继续创建订单。令牌两分钟过期且只能验证一次，因此失败后需重新勾选；前端保留原 `Idempotency-Key`，只更新验证码令牌，防止重复创建收银台。令牌不写入订单、日志或浏览器会话存储。协议见 [Google 服务端验证文档](https://developers.google.com/recaptcha/docs/verify)。

浏览器需要访问 Google reCAPTCHA 和 gstatic，服务器需要访问 `https://www.google.com/recaptcha/api/siteverify`。加载失败会提示重载；不会自动跳过验证。购买页 CSP 只增加验证码所需的脚本、连接与框架来源，报告页仍禁止外部框架，配置依据见 [Google CSP 说明](https://developers.google.com/recaptcha/docs/faq)。

### 4.5 请求限流的范围

两个限额分别按访客 IP 计数，创建订单与读取互不占用额度；读取包括 `/api/orders/status/`、`/success/` 和 `/report/`。超过限额返回 429 和 `Retry-After: 60`，购买按钮与状态轮询会等待后再允许重试。阈值调整后需重启。

计数仍在单进程内存中，重启清空，不跨实例共享；公司或家庭共用出口 IP 时也共用额度。首页、静态文件、健康检查和 Creem 支付回调不占这两个额度；回调由验签和报文大小限制保护。若需要入口抗大流量攻击，可在代理或 CDN 另行配置规则，支付回调应保留独立策略，不能加浏览器人机验证。当前实现未部署集中式限流或修改线上 CDN。

## 5. 使用 Docker Compose 部署

### 5.1 准备服务器

使用一台能持续运行 Docker 和 Compose 的 Linux 主机，项目目录和数据卷位于持久磁盘。服务器需要访问配置的模型服务、行情/新闻数据源、Creem 和 Resend。容器运行环境由 Dockerfile 提供，无需在宿主机再安装 Python 依赖。

把项目放在固定部署目录，从该目录执行后续命令，并准备好 `.env`。Compose 使用该文件中的 `CREEM_MODE` 选择测试或正式 Creem 配置，修改后重建容器即可。下面命令都明确指定 `tradingagents-mvp`，避免把仓库里的原有交互式 CLI 服务一起启动。

```sh
docker compose --profile mvp config --quiet
docker compose --profile mvp up -d --build tradingagents-mvp
docker compose --profile mvp ps tradingagents-mvp
docker compose --profile mvp logs --tail 100 tradingagents-mvp
```

首次构建会安装 Python 依赖。`-d` 表示后台运行，`--build` 表示构建镜像，命令含义见 [Docker Compose 官方说明](https://docs.docker.com/reference/cli/docker/compose/up/)。

### 5.2 端口、目录及配置覆盖

| 项目 | 当前 Compose 配置 |
| --- | --- |
| 容器内监听 | `0.0.0.0:8000` |
| 宿主机暴露 | 仅 `127.0.0.1:8000`，外网不能直接连接 |
| 容器数据根目录 | `/home/appuser/.tradingagents/commerce` |
| 持久化卷 | Compose 中声明的 `commerce_data`，挂载到 `/home/appuser/.tradingagents` |
| 服务进程数 | 1 |
| 退出等待 | 30 秒；不保证运行很久的模型调用能在此期间完成 |
| 重启策略 | `unless-stopped` |

**Compose 在 `environment` 中显式写了 `COMMERCE_DATA_DIR`，它会覆盖 `.env` 中的同名项。** 如果 Docker 部署要换存储目录，需要同时调整 Compose 的数据目录和必要的卷挂载，不能只改 `.env`。新路径仍应落在持久化卷内。

实际卷名通常带 Compose 项目名前缀。部署目录名、项目名或 `-p` 参数变化可能导致使用另一份空卷，看起来像数据消失。因此保持现有项目名和卷一致，迁移时先确认原数据在哪里。

### 5.3 健康检查

在宿主机执行：

```sh
curl --fail http://127.0.0.1:8000/health/live
curl --fail http://127.0.0.1:8000/health/ready
```

后台健康但任务容量不足时，就绪接口响应类似：

```json
{"ready": true, "acceptingOrders": false}
```

`ready=true` 表示数据库和后台线程可用；`acceptingOrders=true` 还要求队列允许新购买。必要配置已在启动前校验。两者都不证明真实支付、行情、模型或邮件服务能成功完成请求。

### 5.4 停止、更新与配置生效

停止服务但保留数据：

```sh
docker compose --profile mvp stop tradingagents-mvp
```

更新代码后重新构建：

```sh
docker compose --profile mvp up -d --build tradingagents-mvp
```

修改 `.env` 后重新创建容器，使环境变量生效：

```sh
docker compose --profile mvp up -d --force-recreate tradingagents-mvp
```

单纯 `restart` 不会把修改后的 `.env` 注入既有容器。重建/重启可能中断正在执行的分析，应安排在空闲期；等待中的任务和已完成报告会保留。当前没有不中断任务的热更新或一键排空功能。

不要对有订单数据的部署使用 `docker compose down -v`，它会删除命名卷。也不要删除数据库、WAL 文件或整个数据目录来解决普通启动错误。

## 6. 域名和 HTTPS 入口

### 6.1 请求链路

```text
用户 / Creem
  → https://reports.example.com:443
  → 宿主机上的 HTTPS 反向代理
  → http://127.0.0.1:8000
  → 付费报告服务
```

先把自己的域名 DNS 指向服务器，准备对应的 HTTPS 证书，再把 `COMMERCE_PUBLIC_URL` 设为同一个 HTTPS 域名。这个配置只告诉应用生成什么链接，不会自动购买域名、修改 DNS、申请证书或开放端口。

### 6.2 已有 Nginx 时的配置模板

下面假定 Nginx 安装在宿主机且证书已经取得。把域名和两个证书文件路径换成自己的值，再加入已有 Nginx 配置；不要覆盖其他站点的配置。

```nginx
server {
    listen 80;
    server_name reports.example.com;
    access_log off;
    return 301 https://reports.example.com$request_uri;
}

server {
    listen 443 ssl;
    server_name reports.example.com;
    ssl_certificate /etc/letsencrypt/live/reports.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/reports.example.com/privkey.pem;

    # 私密报告和状态路径包含访问凭证，避免进入常规访问日志。
    access_log off;
    client_max_body_size 64k;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
        proxy_cache off;
    }
}
```

`proxy_pass` 转发到本机应用，`proxy_set_header` 传递必要头部，相关配置见 [Nginx 官方文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。报告分析在后台进行，不需要让 HTTP 连接保持十几分钟。

在服务器上校验并重载配置：

```sh
sudo nginx -t
sudo systemctl reload nginx
```

此模板假定只有这一层代理直接面对用户。若还经过 CDN、负载均衡或容器内代理，应按实际链路重新设置真实 IP；容器里的 `127.0.0.1` 也不是宿主机地址。

### 6.3 真实 IP 与私密链接

原生 Python 服务由本机 Nginx 访问时，通常信任 `127.0.0.1`。Docker 端口转发后，应用看到的代理来源可能是 Docker 网络网关，需要把实际地址加入 `COMMERCE_FORWARDED_ALLOW_IPS`，再重新创建容器。

可以查询当前容器的网络网关作为排查线索；最终仍要按实际部署链路确认：

```sh
docker inspect --format '{{range .NetworkSettings.Networks}}{{println .Gateway}}{{end}}' \
  "$(docker compose --profile mvp ps -q tradingagents-mvp)"
```

不要为了省事信任 `*`。如果所有用户共用限流额度，优先检查代理识别。应用已关闭常规访问日志；代理、CDN 和运维错误日志也可能包含私密路径，应限制访问并避免对外分享完整内容。不要为报告和状态页面开启 CDN 缓存。

换域名时，已发送和已冻结待发邮件中的地址不会自动改写；尽可能保留旧域名，使原来的报告链接继续可访问。

## 7. 按订单离线查询和导出

这些命令直接读取数据库，不需要启动网站，不调用 Creem、Resend 或模型。必须指向真正保存订单的目录；目录不对时，不要通过新建一个空库来“修复”。

### 7.1 本机命令

```sh
tradingagents-mvp orders --limit 30
tradingagents-mvp orders --status COMPLETED --ticker RXRX
tradingagents-mvp orders --status FAILED
tradingagents-mvp order ORDER_ID
tradingagents-mvp export ORDER_ID --output ./RXRX-report.md
```

`orders` 返回列表，其中 `id` 就是本地订单号。`order` 和 `export` 除了本地订单号，也接受完整的 Creem 支付订单 ID 或收银台 ID。订单详情里的 `report_saved=true` 表示数据库已经保存正文。

详情命令不直接输出付款邮箱和私密访问令牌。`report_path` 是归档文件位置；即使该文件不在了，只要正文快照仍在，仍可以 `export` 导出。

指定另一份数据目录时，`--data-dir` 必须放在子命令前面：

```sh
tradingagents-mvp --data-dir /srv/tradingagents/commerce orders
tradingagents-mvp --data-dir /srv/tradingagents/commerce order ORDER_ID
tradingagents-mvp --data-dir /srv/tradingagents/commerce export ORDER_ID --output ./report.md
```

`/srv/tradingagents/commerce` 是示例路径，请换成实际目录。导出不覆盖已有文件，父目录需要事先存在；重复导出时换一个文件名。

### 7.2 Docker 中查询和导出

服务运行时：

```sh
docker compose --profile mvp exec --user appuser tradingagents-mvp tradingagents-mvp orders
docker compose --profile mvp exec --user appuser tradingagents-mvp tradingagents-mvp order ORDER_ID
docker compose --profile mvp exec --user appuser tradingagents-mvp \
  tradingagents-mvp export ORDER_ID --output /tmp/report-export.md
docker compose --profile mvp cp tradingagents-mvp:/tmp/report-export.md ./report-export.md
```

导出命令中的 `/tmp/report-export.md` 是容器内部路径，所以还要复制到宿主机。`cp` 的服务与本机路径语法见 [Docker 官方说明](https://docs.docker.com/reference/cli/docker/compose/cp/)。

服务停止时仍可启动一次性的离线命令容器读取同一数据卷：

```sh
docker compose --profile mvp run --rm --no-deps tradingagents-mvp tradingagents-mvp orders
```

这里执行的是 `orders`，不会启动分析线程。不要把离线命令误换为第二个 `serve`。

## 8. 备份与恢复

### 8.1 应该备份什么

数据库备份包含订单、完整报告正文、参数、支付通知和邮件记录，可以恢复已归档报告的访问与导出。若还要保留原始分章节报告、缓存、日志和未归档任务的原始文件，应在停止服务后额外备份整个数据目录。

运行中的 SQLite 可能把最新数据写在 WAL 文件里。不要只复制一个正在使用的 `runs.sqlite3`；使用下面的 `backup` 命令生成一致的数据库备份。备份中有付款邮箱和访问令牌，按私有数据保管。

### 8.2 本机备份

```sh
mkdir -p ./backups
backup_file="commerce-$(date +%Y%m%d-%H%M%S).sqlite3"
tradingagents-mvp backup --output "./backups/$backup_file"
```

若当前数据不在默认位置，在 `backup` 前加 `--data-dir`。命令拒绝覆盖已有文件。生成后把备份复制到另一台主机或另一处持久存储；只放在同一块磁盘上不构成独立备份。

### 8.3 Docker 备份

```sh
mkdir -p ./backups
backup_file="commerce-$(date +%Y%m%d-%H%M%S).sqlite3"
docker compose --profile mvp exec --user appuser tradingagents-mvp \
  tradingagents-mvp backup --output "/tmp/$backup_file"
docker compose --profile mvp cp "tradingagents-mvp:/tmp/$backup_file" "./backups/$backup_file"
```

必须完成第二步复制，容器 `/tmp` 里的文件可能在重建后消失。宿主机 `./backups` 也需要再做异地或异盘保存。

### 8.4 恢复前先确认订单和邮件

停止旧服务，保留旧目录和数据卷，不要覆盖原库。选择新的空目录恢复。恢复旧备份会回到备份时刻：这之后已付款、已完成或已发出的事件可能尚未记入备份。

先离线核对备份中的 `PAID`、`RUNNING` 订单及待发送邮件，并对照 Creem、Resend 和旧实例记录确认。**恢复后启动服务会继续执行排队任务和待发邮件，应在启动前完成离线核对。** 旧备份无法自动保证外部已经完成的操作不再发生，需要人工对账。

已在数据库归档的报告不依赖旧绝对文件路径，恢复后仍可查看。未归档的已完成任务若缺少原始文件，会归档失败；正在运行的任务会按中断处理。

### 8.5 本机恢复示例

先停止服务。下面的备份文件名需要换成真实文件；新目录必须尚不存在：

```sh
restore_dir="$HOME/.tradingagents/commerce-restored-20260913"
mkdir "$restore_dir"
cp ./backups/commerce-backup.sqlite3 "$restore_dir/runs.sqlite3"
tradingagents-mvp --data-dir "$restore_dir" orders --status PAID
tradingagents-mvp --data-dir "$restore_dir" orders --status RUNNING
tradingagents-mvp --data-dir "$restore_dir" emails
```

离线确认旧订单能查询和导出后，把 `.env` 的 `COMMERCE_DATA_DIR` 改成这个新目录的绝对路径，再按订单对应的 Creem 模式启动服务并检查报告链接。保留原域名和原令牌，旧报告链接才方便继续使用。

### 8.6 Docker 恢复示例

以下示例使用同一数据卷内的新目录，旧的 `commerce` 目录保留。操作前完成上一节的对账要求，并确认备份文件真实存在：

```sh
docker compose --profile mvp stop tradingagents-mvp
docker compose --profile mvp run --rm --no-deps tradingagents-mvp \
  mkdir /home/appuser/.tradingagents/commerce-restored-20260913
docker compose --profile mvp cp ./backups/commerce-backup.sqlite3 \
  tradingagents-mvp:/home/appuser/.tradingagents/commerce-restored-20260913/runs.sqlite3
docker compose --profile mvp run --rm --no-deps tradingagents-mvp \
  tradingagents-mvp --data-dir /home/appuser/.tradingagents/commerce-restored-20260913 orders
```

只修改 `docker-compose.yml` 中该服务的现有 `environment` 配置，使 `COMMERCE_DATA_DIR` 指向 `/home/appuser/.tradingagents/commerce-restored-20260913`；保留其他配置和原来的卷挂载。离线核对完成并确认 `CREEM_MODE` 与恢复的订单一致后，再执行：

```sh
docker compose --profile mvp up -d --force-recreate tradingagents-mvp
```

如果复制文件后出现属主权限问题，容器启动入口会修正 `/home/appuser/.tradingagents` 下的属主。不要因此把数据库改为所有人可写。

## 9. 邮件失败、退款和人工处理

### 日志查看与排查

通过 `tradingagents-mvp serve` 启动时，默认输出 INFO 级别业务日志到标准错误，包含时间、级别、模块、线程和说明。浏览器下单、Creem、Google reCAPTCHA、支付回调和 Resend 的请求/响应明细在 INFO 级别就会输出，包括接口、脱敏报文、HTTP 状态、耗时和可用的服务商请求号。需要重复通知等 DEBUG 事件时，使用 `tradingagents-mvp serve --log-level debug`；可选级别为 `debug`、`info`、`warning`、`error`。该配置面向 MVP 和付费业务模块，不会因此开启第三方 SDK 的请求调试日志。

Docker 中查看最近日志或持续跟踪：

```sh
docker compose --profile mvp logs --tail 200 -f tradingagents-mvp
```

用本地订单号串起创建、付款、分析和邮件记录，下面的 `ORDER_ID` 换成实际订单号：

```sh
docker compose --profile mvp logs --no-color tradingagents-mvp | rg 'order_id=ORDER_ID'
```

每次 HTTP 请求由服务器生成 `trace_id`，通过响应头 `X-Request-ID` 返回。下单处理、线程池中的验证码校验、Creem 请求和响应共用这个追踪号；前一次调用的追踪号不会被后一次复用。找到订单日志后，可以再按 `trace_id=追踪号` 查看该次调用的完整交互。Creem 和 Resend 的单次外部调用还带 `exchange_id`；后台邮件通过 `order_id` 和 `delivery_id` 与订单关联。

例如，Creem 返回的环境与当前配置不一致时，日志包含以下信息（示例省略公共时间前缀）：

```text
event=creem_response trace_id=示例追踪号 data={"method":"POST","path":"/v1/checkouts","http_status":200,"elapsed_ms":123,"response":{"id":"ch_example","mode":"prod"}}
event=checkout_validation_failed trace_id=示例追踪号 data={"order_id":"示例订单号","failed_checks":["mode_matches"],"expected":{"mode":"test"},"response":{"mode":"prod"}}
```

`checkout_validation_failed` 会列出具体失败项：收银台 ID 缺失、请求订单号不匹配、环境不匹配、商品不匹配或收银台链接无效。请求超时则记录异常类型和耗时；非 JSON 响应标记 `body_format=non_json`，不把上游 HTML 或异常原文写入日志。

| 日志事件 | 含义 |
| --- | --- |
| `order_created` / `checkout_ready` | 本地订单创建 / 收银台创建成功 |
| `http_request` / `http_response` | 下单或 Webhook 的入站请求/响应状态；包括来源拒绝、限流等提前返回 |
| `purchase_request` / `purchase_response` | 已通过结构校验的下单输入及脱敏后的返回内容 |
| `creem_request` / `creem_response` | Creem 商品查询、收银台创建及支付信息查询的脱敏请求/响应 |
| `checkout_validation_failed` / `checkout_uncertain` | 具体不匹配项及预期/实际字段；创建结果不确定的原因 |
| `recaptcha_request` / `recaptcha_response` | Google 验证请求及 `success`、`hostname`、`error-codes` 等结果 |
| `market_data_request` / `market_data_response`（商业模块） | 配置供应商的股票资格查询；记录 `provider`、代码、`quote_type`、交易所、国家及是否允许购买 |
| `market_data_request_failed` | 股票资格查询异常；查看供应商、`error_type`、可用的 `error_code`、`http_status` 和耗时，错误码缺失时为 `null` |
| `market_data_request`（`dataflows.fmp` / `dataflows.marketstack` 模块） | 每次供应商请求的 `endpoint`、`attempt`、`status`、`elapsed_ms`；FMP 还记录返回行数，包含分页和重试，不输出密钥或上游响应正文 |
| `market_data_result` | 行情实际供应商、证券代码、缓存命中、记录数和最新交易日 |
| `webhook_request` / `webhook_response` | 验签且结构校验通过后的支付通知内容及处理结果 |
| `resend_request` / `resend_response` | 邮件服务请求、响应状态和消息 ID，关联订单和交付 ID |
| `payment_recorded` / `analysis_queued` | 付款处理结果提交 / 分析任务入队，带任务号 `run_id` |
| `order_state_saved` | 订单执行状态已提交，失败时查看 `error_type` 和 `run_status` |
| `email_delivery_saved` | 邮件发送记录已保存，`SENT` 表示服务商已接受，不保证最终进入收件箱 |
| `email_retry_expired` | 自动重试窗口到期，需要核对 Resend 后人工处理 |
| `webhook_signature_invalid` | 支付通知验签失败，检查两端签名配置 |
| `creem_http_failed` / `resend_http_failed` | 外部接口失败，查看 HTTP 状态码 |

`serve --log-level` 当前只配置商业和 MVP 模块；`dataflows.fmp`、`dataflows.marketstack`、`dataflows.market_data` 的 INFO 日志需在测试启动器中显式启用对应 Python logger，不能假定默认服务日志已经包含每次行情请求。[FMP 烟测示例](#113-fmp-真实接口验收)演示了该配置。适配器日志为供应商请求明细，不包含订单追踪号；按模块和测试时间窗口统计。

成功入队和状态保存日志在数据库事务提交后输出；正常轮询不会重复输出状态日志。交互报文保留结构、对象 ID、状态、金额、币种等协议字段；密钥、验证码令牌、幂等键、邮箱、姓名、邮件正文及未知自由文本显示为 `[redacted]`。URL 只保留协议和主机，隐藏路径、查询参数和凭据。日志限制嵌套深度、集合长度和单条大小，使用 JSON 转义，避免异常内容污染多行日志。未通过验签的 Webhook 不记录报文，常规访问日志仍关闭。

新增日志只覆盖重启后的调用，不能还原历史上已经丢弃的上游响应。历史 `UNKNOWN` 订单仍需核对 Creem 记录；增加日志不会自动重发创建收银台请求或改变支付校验结果。

前端提示 `Market data is temporarily unavailable.` 表示下单前通过证券资料适配层查询所配置供应商时发生异常，可能是缺少密钥、权限或额度不足、超时等。即使验证码和 Creem 商品查询均成功，也会在此处停止，不创建本地订单或收银台。按同一 `trace_id` 找 `market_data_request_failed`，结合 `provider` 和数据源日志定位。空资料或无法确认类型时也会拒绝购买，并可能提示 `We could not verify this stock.`；已明确为 ETF 或不支持的上市交易所时返回 422。校验失败没有创建订单，用户稍后可使用相同请求标识重试。

应用不另外创建日志文件；本机运行可由进程管理器收集标准错误。Docker 的 MVP 服务配置了 `json-file` 日志轮转，单文件上限 `10m`、最多 `3` 个文件；修改后需重建容器生效。日志轮转不等于长期归档，重要故障记录应另行保存。离线订单查询和导出命令保持原有输出格式。

### 查询与人工处理命令

```sh
tradingagents-mvp orders --status FAILED
tradingagents-mvp emails
tradingagents-mvp events
```

`emails` 列出待发送、发送中和失败邮件；不会列出已成功接受的邮件。`events` 列出被拒绝的支付通知，不是全部事件流水。Docker 运行时，在这些命令前加 `docker compose --profile mvp exec --user appuser tradingagents-mvp`。

| 情况 | 处理步骤 |
| --- | --- |
| 已付款但订单还在等支付 | 用 Creem 收银台/支付订单 ID 查询本地订单，核对 Webhook 的域名、签名和返回结果 |
| Webhook 返回 200 但没有任务 | 查看响应中的 `result`；可能是 `REJECTED` 或 `IGNORED`，再用 `events` 查看原因 |
| 分析失败或重启中断 | 查询订单及原任务日志，人工在 Creem 处理退款；系统没有自动退款按钮 |
| 全额退款 | Creem 通知验证通过后订单变 `REFUNDED`，撤销公开访问，但已保存报告仍能离线导出 |
| 报告完成但没收到邮件 | 先确认报告存在，再查 `emails` 和 Resend 的接受、投递、退信情况；不要因此重新运行分析 |
| 收银台创建结果 `UNKNOWN` | 先到 Creem 核对是否已创建/付款，不要盲目重建订单或要求用户再次付费 |

确实需要人工重发邮件时，先在 Resend 确认旧邮件没有被接受，再执行：

```sh
tradingagents-mvp retry-email DELIVERY_ID --checked-provider
```

`DELIVERY_ID` 来自 `emails` 输出中的 `id`。命令只处理完成或失败订单下的失败邮件，会使用新请求标识重新排队，并保留原来固定的邮件内容；不重新生成报告。它不会自动改写旧邮件中的域名或收件人。

Resend 对同一幂等标识的去重窗口是 24 小时，本系统超过首次尝试 23 小时会停止自动重试，避免重复发送。服务商确认见[官方说明](https://resend.com/docs/dashboard/emails/idempotency-keys)。

## 10. 常见问题

| 现象 | 优先检查 |
| --- | --- |
| `command not found: tradingagents-mvp` | 是否激活 `.venv`；是否安装当前项目；可用 `python -m tradingagents.mvp.cli` 替代 |
| 缺少 `fastapi` 或 `nh3` | 安装 `.[mvp]`，检查安装和启动是否使用同一个 Python 环境 |
| `No module named pip` | 已有 uv 环境可用 `uv pip install --python .venv/bin/python -e '.[mvp]'` |
| 端口被占用 | 使用空闲端口，同时调整 `COMMERCE_PUBLIC_URL` 与 `--port` |
| 启动报 `Missing configuration` | 按错误中变量名补齐当前模式的 Creem 配置及共用邮件、人机验证配置；无需填写未选中的另一模式 |
| 首页显示 `Reports temporarily unavailable` | 检查任务容量、超时未结束的任务和后台线程 |
| `.env` 改了没有变化 | 检查系统环境同名变量覆盖；本机重启进程，Docker 重新创建容器 |
| 数据目录改了仍读旧库 | 检查 Compose 的 `environment` 是否覆盖 `.env` |
| 查不到原来的订单 | 核对系统用户、数据目录、Compose 项目名及卷，避免误读空库 |
| `Another commerce worker owns this directory` | 同一目录已有服务进程；先停止重复实例，不要删除锁文件或数据库 |
| `Origin not allowed` | 浏览器当前站点的协议、域名和端口需与 `COMMERCE_PUBLIC_URL` 一致 |
| HTTP 429 | 触发每 IP 限流；若不同用户互相影响，检查可信代理及真实 IP |
| 验证组件无法加载 | 检查浏览器能否访问 Google/gstatic、CSP 是否被代理覆盖，以及网站密钥是否属于 v2 复选框类型 |
| 下单 403（验证失败） | 重新勾选；检查验证码域名与 `COMMERCE_PUBLIC_URL`，勿复用已过期或已使用的令牌 |
| 下单 503（人机验证不可用） | 检查服务端密钥与 Google 验证接口连通性，服务不会自动绕过验证 |
| 下单 503（股票资格无法确认） | 检查 `instrument_data` 及工具级覆盖、供应商密钥/权限/额度、证券类型和交易所字段；不会绕过校验收款 |
| 配置 FMP 后仍出现 Yahoo 请求 | 检查全部五个选择器、工具级覆盖及旧订单快照；指标选 `local`，不要选 `yfinance` 或 `default`。Marketstack 只替代行情和资料，不能替代其他分类 |
| FMP/Marketstack 返回限流、无权限或额度耗尽 | 临时限流、超时和服务端错误最多重试两次；鉴权、套餐权限和额度耗尽不重试。FMP 的 402 表示当前请求不在套餐内 |
| FMP/Marketstack 行情缺失或过期 | 检查证券是否为支持的美国上市标的、复权字段是否齐全、最新交易日及历史范围；不会混用未复权价格或旧 Yahoo 缓存 |
| Webhook 401 | 验签失败，检查是否用错环境/签名密钥，代理是否改变请求内容 |
| Webhook 503 | 临时查询或数据库问题、找不到本地订单；保留数据，查依赖及恢复情况后让通知重试 |
| 报告 404 / 410 / 503 | 分别检查令牌和目录、是否已全额退款、已完成订单是否缺少正文快照 |
| `Output already exists` | 导出或备份文件已存在，换新文件名；不会覆盖旧文件 |
| Docker 被标记 unhealthy | 查数据库权限和两个后台线程；健康检查不等于长任务正常，进程仍存活时也不会仅因 unhealthy 自动重启 |

### 11.3 FMP 真实接口验收

使用具有所需接口权限的实际 FMP Key 做小规模验证，再决定是否启用正式部署。真实调用消耗额度。以下命令读取 `.env`，只修改本次 Python 进程的配置；不调用模型、不创建订单、不发起付款，也不会改变本地 CLI/Web 默认值。

```sh
python - <<'PY'
import logging
import os
import time
from copy import deepcopy
from datetime import datetime
from tempfile import TemporaryDirectory
from zoneinfo import ZoneInfo

import pandas as pd
from dotenv import load_dotenv

load_dotenv(".env", override=False)
assert os.getenv("FMP_API_KEY"), "请先配置 FMP_API_KEY"
from tradingagents.default_config import DEFAULT_CONFIG
from tradingagents.dataflows.config import set_config
from tradingagents.dataflows.interface import route_to_vendor
from tradingagents.dataflows.market_data import get_instrument_info, get_ohlcv

class RequestMetrics(logging.Handler):
    def __init__(self):
        super().__init__()
        self.requests = 0
        self.elapsed_ms = 0
    def emit(self, record):
        if record.name == "tradingagents.dataflows.fmp" and record.msg.startswith("market_data_request "):
            self.requests += 1
            self.elapsed_ms += record.args[-1]
        print(record.name, record.getMessage())

metrics = RequestMetrics()
for module in ("tradingagents.dataflows.fmp", "tradingagents.dataflows.market_data"):
    logger = logging.getLogger(module)
    logger.setLevel(logging.INFO)
    logger.addHandler(metrics)
    logger.propagate = False

config = deepcopy(DEFAULT_CONFIG)
config["tool_vendors"] = {}
config["data_vendors"].update(dict.fromkeys(
    ("core_stock_apis", "instrument_data", "fundamental_data", "news_data"), "fmp"))
config["data_vendors"]["technical_indicators"] = "local"
as_of = datetime.now(ZoneInfo("America/New_York")).date().isoformat()
end = pd.Timestamp(as_of) - pd.Timedelta(days=1)
start = end - pd.DateOffset(years=5)
with TemporaryDirectory() as cache:
    config["data_cache_dir"] = cache
    set_config(config)
    started = time.monotonic()
    for symbol in ("AAPL", "MSFT", "BRK.B", "BRK-B", "SPY", "TSM"):
        info = get_instrument_info(symbol, config=config)
        bars = get_ohlcv(symbol, str(start.date()), str(end.date()), config=config)
        missing = [key for key in ("company_name", "quote_type", "exchange", "currency") if not info.get(key)]
        print(symbol, info.get("quote_type"), info.get("exchange"), "missing:", missing,
              bars.attrs["provider"], len(bars), bars["Date"].iloc[-1].date())
        before = metrics.requests
        get_ohlcv(symbol, str(start.date()), str(end.date()), config=config)
        assert metrics.requests == before, "覆盖区间缓存未复用"
    for method, args in (
        ("get_fundamentals", ("AAPL", as_of)),
        ("get_balance_sheet", ("AAPL", "quarterly", as_of)),
        ("get_income_statement", ("AAPL", "annual", as_of)),
        ("get_cashflow", ("AAPL", "quarterly", as_of)),
        ("get_news", ("AAPL", str((end - pd.Timedelta(days=7)).date()), as_of)),
        ("get_global_news", (as_of, 7, 5)),
        ("get_insider_transactions", ("AAPL",)),
    ):
        result = route_to_vendor(method, *args)
        print(method, "chars:", len(result), "N/A fields:", result.count("N/A"))
        assert "Provider: fmp" in result, result
    print("HTTP attempts:", metrics.requests, "request milliseconds:", metrics.elapsed_ms,
          "wall seconds:", round(time.monotonic() - started, 2))
PY
```

验收记录至少包含：

1. AAPL、MSFT、BRK.B/BRK-B、SPY、TSM 的准确身份、类型、上市交易所、最新交易日及缺失字段；无效但格式合法的代码应返回不可用。
2. 五年行情超过 1,000 条时没有截断；用已知拆股/分红区间核对复权价格与原始成交量。分析截止日之后的记录不能进入指标或复盘；周末使用实际最近交易日。
3. 财报披露日期及币种、新闻分页/日期范围和内部人交易日期。TTM/概览的历史查询明确不可用，财报没有披露日期时不能作为历史依据。
4. 在测试部署做少量完整分析，记录每次分析的请求数、重试、缓存命中、请求耗时及总耗时。上面的适配层探测不是完整分析请求量；实际计费额度还需与供应商后台核对。不要开启 HTTP 客户端的密钥调试日志。
5. 用 Creem 测试模式完成股票购买至报告交付，确认 FMP 路由不请求 Yahoo，SPY/未知类型不能创建订单。按第 3.4 节验证回滚和旧订单快照；新配置不能改写已购买任务。
6. 对照商业合同确认实际报告展示、新闻、图表、衍生结果和缓存用途。代码集成完成并不等于取得商业数据授权。

若选择 Marketstack，按第 3.4 节改用其行情和证券资料，保留独立的基本面/新闻配置；行情测试另覆盖 1,000 条每页的翻页与 `item_type`、交易所元数据。本地回归不能代替上述真实接口验收。
